Mobile Vitals

Quality signals for mobile development, inspired by Web Vitals. Helping app developers deliver a great mobile user experience, regardless of whether you're building for iOS or Android.

We've used benchmarks collected from real-world applications to help set goals for these metrics. Answering the question, "what is a best in class mobile experience?"

The Metrics

Cold Start

The time it takes a mobile application to start either immediately after booting, or after the application has been killed or evicted from memory.

Why It's Important

Cold Start represents a user's first experience with your application. Make a good first impression.

How to Measure

// Android Cold Start Measurement
// Method 1: Using ADB command line
adb shell am start -W -n com.example.app/.MainActivity

// Method 2: Using Android Studio Profiler
// 1. Open Android Studio
// 2. Go to Profiler tab
// 3. Select CPU profiler
// 4. Start recording and launch app
// 5. Look for "Application onCreate" timing

// Method 3: Using Trace API in code
public class MainActivity extends AppCompatActivity {
    @Override
    protected void onCreate(Bundle savedInstanceState) {
        Trace.beginSection("ColdStart");
        super.onCreate(savedInstanceState);
        
        // Your app initialization code
        setContentView(R.layout.activity_main);
        
        Trace.endSection();
    }
}

Thresholds

good 200ms - 1s
meh 1s - 3s
bad >3s

How to Measure

// iOS Cold Start Measurement
// Method 1: Using Xcode Instruments
// 1. Open Xcode
// 2. Product > Profile (⌘+I)
// 3. Select "Launch Time" template
// 4. Run and analyze startup time

// Method 2: Using code instrumentation
import os.log

class AppDelegate: UIResponder, UIApplicationDelegate {
    func application(_ application: UIApplication, 
                    didFinishLaunchingWithOptions launchOptions: [UIApplication.LaunchOptionsKey: Any]?) -> Bool {
        
        let startTime = CFAbsoluteTimeGetCurrent()
        
        // Your app initialization code
        setupApp()
        
        let endTime = CFAbsoluteTimeGetCurrent()
        let duration = endTime - startTime
        
        os_log("Cold start time: %f seconds", log: .default, type: .info, duration)
        
        return true
    }
    
    private func setupApp() {
        // Initialize your app components
    }
}

Warm Start

Warm Starts measure how long it takes your application to start when some combination of state and resources is already available in memory. Warm start measures a spectrum of behaviour, as it depends on what resources are available, vs., what's been evicted.

Why it's important

Your users will frequently not be launching your application from scratch. Slow Warm Start performance will contribute to bad perceived performance over time.

How to Measure

// Android Warm Start Measurement
// Method 1: Using ADB with background app
adb shell am start -W -n com.example.app/.MainActivity

// Method 2: Using Android Studio Profiler
// 1. Launch app normally
// 2. Press Home to background it
// 3. Start CPU profiler
// 4. Resume app from recent apps
// 5. Measure "onResume" timing

// Method 3: Using code instrumentation
public class MainActivity extends AppCompatActivity {
    private long resumeStartTime;
    
    @Override
    protected void onResume() {
        resumeStartTime = System.currentTimeMillis();
        super.onResume();
        
        // Measure time to first frame
        getWindow().getDecorView().post(() -> {
            long resumeTime = System.currentTimeMillis() - resumeStartTime;
            Log.d("WarmStart", "Resume time: " + resumeTime + "ms");
        });
    }
}

Thresholds

good 200ms - 1s
meh 1s - 3s
bad >3s

How to Measure

// iOS Warm Start Measurement
// Method 1: Using Xcode Instruments
// 1. Launch app normally
// 2. Press Home to background it
// 3. Product > Profile (⌘+I)
// 4. Select "Launch Time" template
// 5. Resume app from app switcher

// Method 2: Using code instrumentation
class AppDelegate: UIResponder, UIApplicationDelegate {
    private var foregroundStartTime: CFAbsoluteTime = 0
    
    func applicationWillEnterForeground(_ application: UIApplication) {
        foregroundStartTime = CFAbsoluteTimeGetCurrent()
        
        // Resume your app
        DispatchQueue.main.async {
            let endTime = CFAbsoluteTimeGetCurrent()
            let duration = endTime - self.foregroundStartTime
            
            os_log("Warm start time: %f seconds", log: .default, type: .info, duration)
        }
    }
}

Time to Initial Display

The time it takes your application, either from a cold or warm start, to render its first frame of animation to screen.

Why it's important

This metric is a good indicator of when your user perceives your application as having actually launched.

How to Measure

// Android Time to Initial Display
// Method 1: Using GPU Info
adb shell dumpsys gfxinfo com.example.app

// Method 2: Using Android Studio Profiler
// 1. Open Profiler tab
// 2. Select GPU profiler
// 3. Look for first frame in timeline
// 4. Measure from app start to first frame

// Method 3: Using FrameMetrics API
public class MainActivity extends AppCompatActivity {
    @Override
    protected void onCreate(Bundle savedInstanceState) {
        super.onCreate(savedInstanceState);
        setContentView(R.layout.activity_main);
        
        if (Build.VERSION.SDK_INT >= Build.VERSION_CODES.N) {
            getWindow().addOnFrameMetricsAvailableListener(
                new Window.OnFrameMetricsAvailableListener() {
                    @Override
                    public void onFrameMetricsAvailable(Window window, FrameMetrics frameMetrics) {
                        long firstFrameTime = frameMetrics.getMetric(FrameMetrics.FIRST_DRAW_FRAME);
                        Log.d("InitialDisplay", "First frame: " + firstFrameTime + "ns");
                    }
                }, null);
        }
    }
}

Thresholds

good 200ms - 1s
meh 1s - 3s
bad >3s

How to Measure

// iOS Time to Initial Display
// Method 1: Using Xcode Instruments
// 1. Product > Profile (⌘+I)
// 2. Select "Core Animation" template
// 3. Look for first frame in GPU trace
// 4. Measure from app start to first frame

// Method 2: Using CADisplayLink
class ViewController: UIViewController {
    private var displayLink: CADisplayLink?
    private var firstFrameTime: CFTimeInterval = 0
    
    override func viewDidLoad() {
        super.viewDidLoad()
        
        displayLink = CADisplayLink(target: self, selector: #selector(frameCallback))
        displayLink?.add(to: .main, forMode: .common)
    }
    
    @objc func frameCallback() {
        if firstFrameTime == 0 {
            firstFrameTime = CACurrentMediaTime()
            let appStartTime = ProcessInfo.processInfo.systemUptime
            let initialDisplayTime = firstFrameTime - appStartTime
            
            print("Time to initial display: \(initialDisplayTime)s")
            displayLink?.invalidate()
        }
    }
}

Thresholds

good 200ms - 1s
meh 1s - 3s
bad >3s

Time to Full Display

The time it takes your application to actually become useable.

Why it's important

If additional work, e.g., rendering a document, needs to happen before your application becomes useable, this will contribute to your users perceived performance.

How to Measure

// Android Time to Full Display
// Method 1: Using ViewTreeObserver
class MainActivity : AppCompatActivity() {
    private var appStartTime: Long = 0
    
    override fun onCreate(savedInstanceState: Bundle?) {
        appStartTime = System.currentTimeMillis()
        super.onCreate(savedInstanceState)
        setContentView(R.layout.activity_main)
        
        // Wait for layout completion
        findViewById(android.R.id.content).viewTreeObserver
            .addOnGlobalLayoutListener(object : ViewTreeObserver.OnGlobalLayoutListener {
                override fun onGlobalLayout() {
                    val fullDisplayTime = System.currentTimeMillis() - appStartTime
                    Log.d("FullDisplay", "Time to full display: ${fullDisplayTime}ms")
                    
                    // Remove listener to avoid multiple calls
                    findViewById(android.R.id.content).viewTreeObserver
                        .removeOnGlobalLayoutListener(this)
                }
            })
    }
}

Thresholds

good 200ms - 1s
meh 1s - 3s
bad >3s

How to Measure

// iOS Time to Full Display
// Method 1: Using viewDidLayoutSubviews
class ViewController: UIViewController {
    private var appStartTime: CFAbsoluteTime = 0
    private var hasMeasuredFullDisplay = false
    
    override func viewDidLoad() {
        super.viewDidLoad()
        appStartTime = CFAbsoluteTimeGetCurrent()
    }
    
    override func viewDidLayoutSubviews() {
        super.viewDidLayoutSubviews()
        
        if !hasMeasuredFullDisplay {
            let fullDisplayTime = CFAbsoluteTimeGetCurrent() - appStartTime
            print("Time to full display: \(fullDisplayTime)s")
            hasMeasuredFullDisplay = true
        }
    }
}

Frame Delay

When a user interacts with your application, the next frame of animation should render in a reasonable amount of time and, the app falling back into a responsive state. Frame delay is a spectrum, slow frames feel janky, where as truly frozen frames can result in an application feeling unresponsive or hung.

Why it's important

A janky or frozen application feels unstable and, in general, is a bad user experience.

How to Measure

// Android Frame Delay Measurement
// Method 1: Using GPU Info
adb shell dumpsys gfxinfo com.example.app

// Method 2: Using Choreographer
class MainActivity : AppCompatActivity() {
    private var lastFrameTime: Long = 0
    
    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        setContentView(R.layout.activity_main)
        
        Choreographer.getInstance().postFrameCallback(object : Choreographer.FrameCallback {
            override fun doFrame(frameTimeNanos: Long) {
                if (lastFrameTime > 0) {
                    val frameDelay = (frameTimeNanos - lastFrameTime) / 1_000_000 // Convert to ms
                    if (frameDelay > 16.67) { // 60fps = 16.67ms per frame
                        Log.w("FrameDelay", "Frame delay: ${frameDelay}ms")
                    }
                }
                lastFrameTime = frameTimeNanos
                Choreographer.getInstance().postFrameCallback(this)
            }
        })
    }
}

Thresholds

good 200ms - 1s
meh 1s - 3s
bad >3s

How to Measure

// iOS Frame Delay Measurement
// Method 1: Using Xcode Instruments
// 1. Product > Profile (⌘+I)
// 2. Select "Core Animation" template
// 3. Look for frame drops in timeline
// 4. Monitor GPU utilization

// Method 2: Using CADisplayLink
class ViewController: UIViewController {
    private var displayLink: CADisplayLink?
    private var lastFrameTime: CFTimeInterval = 0
    
    override func viewDidLoad() {
        super.viewDidLoad()
        
        displayLink = CADisplayLink(target: self, selector: #selector(frameCallback))
        displayLink?.add(to: .main, forMode: .common)
    }
    
    @objc func frameCallback() {
        let currentTime = CACurrentMediaTime()
        
        if lastFrameTime > 0 {
            let frameDelay = currentTime - lastFrameTime
            let expectedFrameTime: CFTimeInterval = 1.0 / 60.0 // 60fps
            
            if frameDelay > expectedFrameTime {
                print("Frame delay detected: \(frameDelay)s (expected: \(expectedFrameTime)s)")
            }
        }
        
        lastFrameTime = currentTime
    }
}

Thresholds

good 200ms - 1s
meh 1s - 3s
bad >3s

Calculating Mobile Vitals Score

Individual Metrics

The good, meh, bad measurement for each individual metric is calculated based on the observed behaviour of Sentry's corpus of mobile telemetry, along with other telemetry that has been provided by the community.

A score in the 8th percentile or higher, represents good, a score of 25th percentile or higher meh, and a score below the 25th percentile is bad.

Scores are further broken out by Android and iOS, as there's significant variation between the two device types.

Overall Score

Similar to lighthouse performance-scoring, the overall score provides a score between 1 and 100 for Mobile Vitals, based on a log-normal distribution of each weighted score.
